# What is a Grafana Cloud Integration, and what are sample-apps supporting them?
A Grafana Cloud Integration is a prebuilt package of dashboards, recording rules, alerts, metadata, and scrape configurations intended to make it quick to add monitoring to a number of systems. See here for more information on [Grafana Cloud Integrations](https://grafana.com/docs/grafana-cloud/what-are/integrations/) and the [Integrations reference](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/integrations/integration-reference/) for a list of supported systems.

Sample-apps are pre-configured applications and load-testing that allows us to spin up a system for a given integration and quickly validate the metrics emitted match what we expect for our Cloud Integrations.

# Adding CI support to a Multipass based sample-app
Please note, this is not a full tutorial in creating sample-apps from scratch.

Sample-apps are run in CI using Multipass on `ubuntu-latest-8-core`, with both Loki and Mimir spun up outside the sample-app. Nested virtualisation is available, and multiple VMs can be created as desired.

**Workflow timeout is currently set at 30 minutes, and will fail if exceeded**

The CI workflow expects a few things from a CI enabled sample app. For a working example, please check out the [openldap sample-app](/sample-apps/openldap/):

1. Ensure the sample-app is built using Multipass
   - Sample should be stand-alone and not contain any databases
1. Ensure sample-app has load-generation scripts or capabilities to accurately produce metrics for the majority of use-cases
1. Ensure sample-app name matches integration slug
1. Add a directory called `tests`, with subdirectories `metrics` and `configs`
    1. For each test scenario, add a file to the `tests/metrics/` directory, giving it an arbitrary name, with no file-type. It should contain a newline separated list of Prometheus metrics expected by the integration, e.g:
    ```
    up
    metric_name_1
    metric_name_2
    ```
    A `#` starts a comment. Recording rule outputs, named `level:metric:operations` such as `instance:mysql_heartbeat_lag_seconds`, are skipped, since the databases in CI run no recording rules. If a sample-app has several scenarios, name the one that checks the integration's own metric list `integration`: a caller replacing the app's list with `--metrics` replaces that one.

    2. Add a matching config file to the `tests/configs/` directory, reusing the same name as the metrics file, but with the `.config` filetype
    - Set the `JOB_LABEL` variable to match the integration's job label
    - [Optional] Set `INSTANCE_FILTER` to a space-separated list of `instance` label regexes, e.g. `".*-alloy.* .*-otelcol.*"`. The metrics are checked separately for each regex, and every one must pass. Useful when a sample app runs several collectors or hosts under the same job label. Each check passes if any matching instance reports the metric. (Default: unset, which checks the whole job)
    - [Optional] Set `METRICS_SUCCESS_RATE_REQUIRED` to define the required percentage of metrics that has to be generated by the sample app, as compared to the metrics contained within `expected_metrics`. E.g. if 100% of expected metrics must be generated by the sample app, with no deviation allowed, set this value to `1.0`. (Default: `0.8` for 80% match)
    - Values follow `.env` syntax. Put a value in single quotes if it contains a backslash or a `$`, e.g. `INSTANCE_FILTER='.*\.internal'`
1. Makefile
    1. Should be present in sample-app dir
    1. Variables should be created for logs and metrics database hosts, e.g: 
        ```
        LOKI_INSTANCE ?= your-loki-instance:3100
        PROMETHEUS_INSTANCE ?= your-prometheus-instance:9090
        ```
    1. `make run-ci` must be a valid make option, making use of the variables defined in 2., such that a clean cloud-init or similar configuration is generated and applied, load-testing is run, and so forth depending on sample-app requirements

# Adding dashboard screenshots
A sample-app can list the dashboards of its integration. CI then renders them against the data the sample-app produced and posts the images as a comment on the pull request, so reviewers can see that the dashboards are populated.

Add a `tests/dashboards` file that names the integration's mixin in [grafana/jsonnet-libs](https://github.com/grafana/jsonnet-libs). Every dashboard in the mixin's `dashboards_out` directory on `master` is captured, so dashboards added to the mixin later are picked up without changes here:
```
jsonnet-libs/docker-mixin
```

To capture the dashboards of a jsonnet-libs branch, tag or commit instead, for example while a mixin change is still in review, add `@<ref>`:
```
jsonnet-libs/docker-mixin@my-mixin-branch
```

Dashboards from elsewhere can be listed as one `https://` URL of a dashboard `.json` file per line. Lines starting with `#` are comments.

The comment groups mixin dashboards by their jsonnet-libs ref and then by mixin, with the dashboards listed by URL under each sample-app.

Screenshots cover the 5 minutes before they are taken. Dashboards exported for sharing, which carry `__inputs` datasource placeholders, are skipped.

Listing a mixin uses the GitHub API, which allows 60 requests an hour without a token. Set `GITHUB_TOKEN` to raise the limit; CI does this.

The comment is only posted for pull requests from branches of this repository. For pull requests from forks, the images are attached to the workflow run as the `screenshots-<sample-app>` artifact instead.

# Excluding your sample-app from CI runs
In some cases, such as sample-apps relying on cloud providers, externally hosted services, or other such edge-cases it may be impossible to automatically spin up and test them with Github Actions.

Should this be the case, you **must add** a blank `.CI_BYPASS` file to your sample-apps directory. If this file is not present, the Github Actions workflow will run and fail your changes.
# Running sample-apps from another repository
`.github/workflows/sample-app.yml` runs sample-apps and checks their metrics, as pull requests here do. Another repository can call it to test its own version of an integration's metric list against the integration's sample-app. The run, and its logs, belong to the calling repository.

```yaml
jobs:
  metric-lists:
    runs-on: ubuntu-latest
    steps:
      # One file per sample-app, named after it, in the same format as tests/metrics
      - run: mkdir -p lists && cp path/to/mysql/metric-list lists/mysql
      - uses: actions/upload-artifact@<sha> # pin a version
        with:
          name: expected-metrics
          path: lists/

  sample-apps:
    needs: [metric-lists]
    permissions:
      contents: read
    uses: grafana/integration-sample-apps/.github/workflows/sample-app.yml@<sha>
    with:
      apps: '["mysql"]'
      metrics-artifact: expected-metrics
```

- `apps` is a JSON array of sample-app names. Apps that CI can't run, with a `.CI_BYPASS` file, pass without running.
- `ref` picks the branch, tag or commit of this repository to run the sample-apps from, by default `main`. Point it at a pull request's head to test a change that needs one here as well.
- `metrics-artifact` names an artifact of the calling run, holding `<app>` or `<app>/<scenario>` files. They replace the apps' own `tests/metrics` files, as `sampletool apps test --metrics` does, while the scenario's config still applies.
- `runner` must support nested virtualization, by default `ubuntu-latest-8-cores`.

Screenshots are uploaded as `screenshots-<app>` artifacts of the calling run.
